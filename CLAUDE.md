# Симуляция умного пешеходного перехода (CARLA)

## Контекст

Хакатон «Цифровая Эра Транспорта», кейс ООО «Смарт Си»: умный регулируемый пешеходный переход.
Вместо жёсткого цикла или кнопки система по видеоаналитике (YOLO) считает пешеходов и машины
и решает, когда включать пешеходную фазу: учитывает плотность потока, минимальную задержку
при пустой дороге, приоритет для групп пешеходов (5–10 человек), аварийный режим при потере камеры.

Моя часть в команде — симуляция: реалистичный мир, в котором работает наш контроллер.
Нейронку (YOLO) делает другой человек, интерфейс и презентацию — остальные.

## Окружение

- CARLA 0.9.16 (готовый пакет, UE4), Linux-десктоп с NVIDIA. Сервер на `localhost:2000`.
- Python venv, пакет `carla==0.9.16` (версия клиента обязана совпадать с сервером).
- Карта: **Town05**.

## Архитектурный принцип

CARLA — это только «мир»: машины, пешеходы, светофоры, камеры.
Вся логика (контроллер фаз, статистика, позже YOLO) живёт в Python-процессе снаружи
и общается с миром через API. Контроллер должен быть отделён от симулятора,
чтобы потом его можно было запускать на реальных данных.

## Выбранный участок

- T-образный перекрёсток в Town05. Переход через дорогу 2+2 на въезде в примыкающую дорогу.
- Центр зебры: примерно `(32.3, -178.5)`.
- **Наш светофор** — тот, чья стоп-линия ближе всего к зебре. Остальные светофоры его группы
  (`get_group_traffic_lights()`) — главная дорога.
- Рядом есть ещё мелкий перекрёсток с примыкающей дорогой, его светофор держим зелёным
  (все светофоры вне нашей группы — зелёные).

## Файлы

- `main.py` — разведчик. По точке CENTER находит и рисует в мире ближайшие светофоры
  (id, стоп-линии), три ближайших перехода (контуры) и точки спавна, смотрящие к центру.
- `find_crossings.py` — поисковик. Перебирает все светофоры карты, считает полосы на подходе
  через `get_waypoint_xodr`, ищет рядом переход, выводит кандидатов. `--goto <id>` переносит
  камеру к светофору, `--map` загружает карту.
- `run_scene.py` — основная сцена:
  - синхронный режим, `DT = 0.05` (world и Traffic Manager);
  - находит наш светофор по позиции, замораживает все светофоры (`freeze_all_traffic_lights`),
    каждый тик спрашивает `controller.py`, что должно гореть, и ставит цвета: `MAIN` (едет главная),
    `SIDE` (едет наша дорога), `YELLOW` (жёлтый той, что ехала), `ALL_RED` (очистка), `PED` (всем красный);
    раз в 0.5 с собирает контроллеру `Traffic`: очередь до зебры из `Observer.queue()` (коридор JSON),
    пешеходов из `peds.demand()`, интенсивность нашей дороги по машинам в коридоре за 5 мин;
  - **источник** машин: пуассоновский поток (`VEH_PER_HOUR`) на точках спавна в кольце 40–150 м,
    смотрящих к перекрёстку; точка считается занятой, если рядом машина ближе 10 м;
  - **сток**: машины дальше 170 м удаляются;
  - раз в секунду печатает фазу, число машин в зоне, сколько ждёт у нашей стоп-линии;
  - в `finally` удаляет акторов, размораживает светофоры, возвращает асинхронный режим.
  - Проверено: работает стабильно, очередь растёт на красный и рассасывается на зелёный каждый цикл.
  - `PED` = 20 с (переход ~17–18 м, нужно 13–17 с с запасом).
- `controller.py` — контроллер фаз, перенесён из backend сокомандника (`backend/app/simulation/signal.py`,
  `adaptive.py`; там FastAPI + Postgres + свой 1D-симулятор, нам нужен только автомат). Про CARLA не знает:
  `Traffic` (что видит камера) → `Signal` (фаза). Режимы `cycle` / `button` / `adaptive` / `manual`
  (`SIGNAL_MODE`, на лету — `set_mode`/`set_manual` через `control.py`). Автоматические режимы — один автомат
  `car_green → car_yellow → clear_to_ped → ped_green → clear_to_car`, отличаются только уходом из `car_green`,
  поэтому смена режима не рвёт пешеходную фазу. `car_green` = MAIN ⇄ SIDE по очереди; после пешеходов едет
  стоявшая дорога; новую дорогу не обрываем раньше `STAGE_MIN_S` (иначе зелёный на 1 тик), а в adaptive
  на границе MAIN/SIDE уходим к пешеходам заранее, если критическое ожидание наступит раньше.
  Отличия от backend (нет трамваев/остановок, PED = `PHASE_PED` во всех режимах, «ждём, пока переход
  свободен» — во всех режимах) — в шапке файла. `cycle` с `PHASE_YELLOW=0` и очистками `0` = старый цикл.
- `pedestrians.py` — пешеходы на нашем переходе, подключены к циклу `run_scene.py`.
  Торцы зебры и точки ожидания W/E ищутся по позиции; пуассоновский поток, не больше 3 живых
  пешеходов с каждой стороны (`MAX_PER_SIDE`; группы 5–10 в лимит не влезают, `GROUP_PROB = 0`);
  своя машина состояний `APPROACH → WAIT → CROSS (только в PED, если успевает) → LEAVE → сток`;
  `demand(t)` отдаёт `PedDemand` (ждут по сторонам, макс/среднее ожидание, группа, перешло) —
  эти же числа потом даст YOLO. `python pedestrians.py` — только геометрия и debug-отрисовка.
- `JSON_FORMAT.md` — согласованный формат сообщений для друга: машины на нашей дороге (тип, полоса 1–4
  с запада на восток: 1–2 от перехода, 3–4 к переходу, скорость) и пешеходы в зонах ожидания W/E
  и на зебре.
- `ws_sender.py` — отдельный процесс: вторым клиентом CARLA только читает мир и рассылает JSON
  по WebSocket (`ws://<ip>:8765`, раз в 0.5 с симуляции). Запускать после `run_scene.py`.
  Геометрию зебры берёт из `pedestrians.find_geometry()` — зоны те же, что у пешеходов.
  Фаза определяется по цветам светофоров: жёлтый — ещё MAIN/SIDE, очистка (всем красный) — уже PED. Нужна `websockets` (ставить `uv pip install`, в venv нет pip).
- `Dockerfile`, `docker-compose.yml` — сцена и отправщик в Docker (`docker compose up --build`),
  сервер CARLA на хосте, `network_mode: host`, `stop_signal: SIGINT` для уборки. Параметры — переменные
  окружения через `envconf.env()` (список — `.env.example`); `run_scene.py` сам грузит `CARLA_MAP`.
  Сборка ещё не проверена: на машине разработки нет Docker (requirements проверены в чистом venv).
- `camera.py` — RGB-камеры на перекрёстке (отдельный процесс, ставит и убирает только свои камеры).
  По умолчанию две: `peds` — на зебру из северо-западного угла (`CAM_PEDS`, поза снята в окне CARLA),
  `cars` — на очередь, авто от геометрии (12 м перед зеброй, 15 м, −35°). `CAM_POSE="…;…"` — свои,
  `--from-spectator`; окно с картинками рядом, `--save DIR` — кадры в `DIR/<камера>/`, `--screenshot`.
  Раздаёт камеры по HTTP как IP-камеры (порт 8080): `/<камера>.mjpg` — MJPEG-поток, `/<камера>.jpg` —
  кадр, `/` — страничка; `--no-window` — только раздача. Адрес печатает из `hostname -I`: маршрут по
  умолчанию у этой машины идёт в VPN-туннель (`tun0`, 172.18.0.1), а локальная сеть — `enp7s0`.
- `debug_view.py` — отладочное окно (pygame), тоже только читает мир: вид сверху, машины по габаритам
  с координатами, полосы и коридор JSON (из `ws_sender.Observer`), зоны W/E, координаты под курсором.
  Ползунки (машин/ч, макс машин, пешеходов/ч, на сторону) и кнопки (режим светофора, ручная фаза) шлют
  сцене команды через `control.py` (UDP JSON, `127.0.0.1:8770`); сцена читает их раз в секунду и отвечает
  текущими значениями, фазой и причиной. Фазу окно берёт у сцены: по цветам очистка = PED.

## Что уже известно (грабли)

- OpenDRIVE standalone (`generate_opendrive_world`) не даёт светофор посреди прямой дороги.
  Полноценная кастомная карта требует сборки CARLA из исходников и ручной расстановки
  светофоров в Unreal Editor — от этого пути отказались, работаем на готовой карте.
- **id акторов меняются после перезапуска сервера / reload_world.** Никогда не хардкодить id,
  всегда искать светофоры по позиции (через стоп-линии и расстояние до зебры).
- Подписи светофоров (debug) рисуются у столба, а не у стоп-линии — по ним легко перепутать.
- `set_state` применяется на следующем тике.
- **Пешеходы CARLA игнорируют светофоры.** Их поведение на переходе нужно делать своей логикой.
- **Debug-отрисовка видна RGB-камерам и засвечивает кадр**: белый контур зебры светится, автоэкспозиция камеры
  «уводит» картинку в белую дымку вокруг зебры (проверено 2026-09-28: та же камера, `DRAW_DEBUG` 1 → засвет, 0 → чисто).
  Поэтому `DRAW_DEBUG` по умолчанию выключен.
- Если скрипт упал без уборки, мир остаётся в синхронном режиме и «замерзает».
- «Пересвет» раньше считали глюком рендера — это была debug-отрисовка (см. выше); `reload_world()` помогал, потому что
  стирал её. **`client.reload_world()` может уронить сервер** (SIGSEGV 2026-09-28) — не использовать.
- **ИИ-пешеход (`controller.ai.walker`) для нашей зебры не годится** (проверено тестами):
  дойдя до цели, сам берёт новую случайную и уходит; у чужих зебр ждёт разрыва в потоке машин
  и по таймауту уходит в случайное место; с тротуара E на нашу зебру не ступает даже при всех красных
  (с W на E проходит). Поэтому пешеходы ручные: `WalkerControl` каждый тик.
- Тело, к которому хоть раз прикрепили `controller.ai.walker`, не слушается `WalkerControl`
  даже после `stop()` и удаления контроллера. Ручное управление — только у тел без контроллера.
- Ручной пешеход не всегда забирается на бордюр у торцов нашей зебры — подсаживаем `set_location` на 30 см.
- Ручные пешеходы соседей не видят: зашёл в другого — физика выталкивает со скоростью ~30 м/с,
  бывает прямо на дорогу. Поэтому правило «не наступать на соседа» (`AVOID_DIST`): впереди ближе
  0.8 м человек — обход на ±60° или ждать. Отключить коллизии нельзя: с `set_collisions(False)`
  пешеход перестаёт ходить (есть в биндинге 0.9.16, в документации нет).
- **RGB-камера, смотрящая вдоль нашей дороги с горизонтом в кадре, роняет сервер** (Signal 11,
  0 кадров; проверено тестами 2026-09-27). Не зависит от разрешения, окна, синхронного режима,
  других клиентов и версии пакета `carla`. Та же точка с наклоном круче ~30° (горизонт вне кадра),
  вид сверху и взгляд в другую сторону — работают. Поэтому в `camera.py` по умолчанию 15 м и −35°,
  а при горизонте в кадре скрипт предупреждает. Спам `Invalid session: no stream available` в логе
  сервера — следствие такого падения, не причина. В другие стороны горизонт в кадре не мешает
  (камера `peds`, −29°, смотрит на юго-восток — работает).
- Сторона E: тротуар по прямой только ~16 м, дальше угол с зеброй соседнего перекрёстка;
  точка ожидания E привязана к краю тротуара в 2.6 м от торца (за торцом тротуара нет).

## Правила для кода

- Не выдумывать API. Сверяться с документацией CARLA 0.9.16 и `PythonAPI/examples`.
  Если метода нет в этой версии — так и сказать.
- Не маскировать молча то, что не работает: отражать в выводе и в ответе.
- Уборка всех своих акторов и возврат настроек мира в `finally` обязательны.
- Код простой и читаемый, короткие комментарии, параметры в конфиге сверху.
- Не ломать существующее поведение `run_scene.py` (машины, фазы, статистика).

## Следующая задача: пешеходы

Добавить пешеходов на наш переход, отдельным модулем (например, `pedestrians.py`),
подключённым к циклу `run_scene.py`.

Требования:
1. **Точки ожидания.** По контуру нашей зебры (из `get_crosswalks()`, ближайший к центру)
   определить два торца перехода (края, откуда пешеход ступает на проезжую часть) и точки
   ожидания на тротуаре с обеих сторон. Проверить привязку к тротуару через
   `map.get_waypoint(..., lane_type=carla.LaneType.Sidewalk)`. Отрисовать эти точки
   debug-ом для проверки глазами (с флагом, чтобы можно было выключить).
2. **Поток.** Пешеходы появляются на тротуаре в 20–40 м от перехода с обеих сторон,
   пуассоновским потоком `PED_PER_HOUR`; с вероятностью `GROUP_PROB` появляется группа
   из 5–10 человек. Параметры в конфиге.
3. **Спавн.** Тело `walker.pedestrian.*` + контроллер `controller.ai.walker`, прикреплённый
   к телу; учесть, что в синхронном режиме между спавном и `controller.start()` нужен `tick`.
   Скорость 1.2–1.6 м/с. Отключить самовольный переход дороги (`world.set_pedestrians_cross_factor`,
   проверить наличие в 0.9.16).
4. **Поведение — своя машина состояний на каждого пешехода:**
   `APPROACH` (идёт к точке ожидания) → `WAIT` (стоит у бордюра) → `CROSS` (идёт на другую
   сторону, только в фазе `PED`) → `LEAVE` (уходит по тротуару) → удаление (сток).
   Не начинать переход, если до конца фазы `PED` осталось меньше времени, чем нужно на переход
   (ширина дороги / скорость + запас).
5. **Статистика** раз в секунду: сколько ждут с каждой стороны, максимальное и среднее время
   ожидания, сколько перешло за всё время. Отдельно — есть ли сейчас группа ≥ 5 человек.
6. Состояние «кто ждёт» должно быть доступно контроллеру фаз как данные (позже эти числа
   будут приходить с камеры/YOLO, а не из симулятора). Сам контроллер пока не менять —
   фиксированный цикл остаётся.
7. Уборка пешеходов и контроллеров в `finally` (сначала `controller.stop()`, потом удаление).

Сначала прочитай существующие файлы, покажи план и найденные торцы/точки ожидания,
потом пиши код. В конце кратко объясни, что сделал и как проверить.
